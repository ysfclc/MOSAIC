## Android-native integration path (no provider API dependency)

- **Session discovery/control:** use Android `MediaSessionManager` with explicit Notification Listener access. Read only active session metadata and advertised transport actions; send play/pause/next/previous/seek to the source app. This is already wired into MOSAIC's primary Player. The original app remains the playback owner.
- **Visible ad skip:** an optional Android AccessibilityService is registered for the YouTube app only. It looks for a visible, enabled control whose text/content description exactly matches a small allowlist of ad-specific labels (English, Polish and Turkish), then clicks the nearest clickable ancestor. It does not click generic “Skip” controls, inspect audio/network content, or claim to remove an ad. Service enablement is explicit in Android Accessibility settings. The service is covered by source/contract checks in CI run #177, but no Redmi/ad-variant/false-positive acceptance is recorded.
- **Device-wide filtering:** the separate local VPN/DNS layer can block known ad/tracker hosts when requests are separable. It cannot reliably block ads delivered from the same host as content.
- **Background continuation:** Android foreground media services keep MOSAIC-owned playback alive. For source-owned playback, MOSAIC can only control the session exposed by the source; an accessibility helper cannot override another app's background-playback policy.
- **Acceptance:** the accessibility service is code-added but not yet CI-verified or tested on the Redmi. Record app version, exact skip label, whether it was clicked, false-positive behavior, screen-off behavior and accessibility permission state before marking it complete.

## Playback modes (must never be conflated)

- **MOSAIC PLAYER:** MOSAIC has a usable media locator and plays the item through its shared Media3 service. It owns the playback queue and app session.
- **BROWSER PLAYER:** the media is played inside MOSAIC's browser surface. Background behavior must be tested; merely loading a page is not support.
- **EXTERNAL PLAYER:** the original app/site owns the media session. MOSAIC can only show/control commands that Android and that source expose. This is useful but not equivalent to MOSAIC receiving the audio.
- **LINK ONLY:** MOSAIC can open or save a reference but has not demonstrated playback.

Each source can expose more than one mode. Capability is per item, account, app version and session where relevant.

## Ad-control layers

1. **Browser filtering:** request-level rules for content loaded inside MOSAIC. Current implementation is a small conservative host list and is not a full filter engine. **Known ADR gap:** `AdBlockPolicy.kt` still short-circuits blocking for YouTube/Spotify page and asset hosts and the regression tests preserve that exemption. This conflicts with ADR-014/015 and PRODUCT_SPEC.md §11's no-blanket-exemption requirement. P3-015 remains TODO until source-aware allow/block rules replace it with compatibility tests; do not call browser filtering complete.
2. **Device-wide filtering:** optional, explicit-consent Android `VpnService` local DNS/host filtering. This is the main cross-app ad-blocking route to investigate and implement.
3. **Source-aware rules:** the intended policy is to block known ad/tracker endpoints even when a first-party content domain is allowed, with measured compatibility. The current Browser policy does not yet meet this requirement because of the legacy protected-provider short-circuit noted above. Device Ad Shield has its own curated DNS rules and editable allowlist.
4. **Measured limits:** DNS/host filtering cannot reliably distinguish ads from content when both share a hostname or are inserted into the media stream. Record these as tested limitations, not as reasons to abandon broader filtering.

## Acceptance evidence required

For every named source, record app/site version, account tier where relevant, Android version/device, route used, playback owner, foreground behavior, screen-off continuation, app-switch behavior, lock-screen/notification/headset controls, seek/queue support, ad requests blocked, content breakage, false positives and known gaps. No capability is DONE based only on a successful page load or metadata display.


## Evidence update — 2026-11-12 (source snapshot at main commit `15e53c7`)

- Code and contract checks confirm native HTTPS stream input (including HLS), bounded RSS/Atom feed loading and parsing, locally persisted feed URLs, direct HTTPS HTML5 Browser-to-Media3 handoff, and a native Media3 video surface. These are source-level capabilities; no real Redmi source/screen-off acceptance is recorded.
- The latest main-branch workflow run #177 (`42261946226`) completed successfully. It ran source verification, 16 Python contract tests, Android unit tests for `:core:media` and `:app`, lint, APK assembly, checksum/signature verification and private prerelease publication. CI success is not device acceptance.
- External YouTube/Spotify playback remains source-owned when represented by Android MediaSession; MOSAIC has not demonstrated a compliant native audio path for those services. Facebook/Instagram behavior remains unverified.
- Device Ad Shield uses the opt-in IPv4 UDP DNS-only VPN path. It does not tunnel ordinary app traffic; DoH/custom DNS/IPv6 and same-host/in-stream ads remain coverage gaps. The dedicated Redmi checklist has not been signed off.

## Evidence update — 2026-11-05

- **Spotify:** Spotify's official [Android SDK documentation](https://developer.spotify.com/documentation/android) describes App Remote as a way to read current playback state and issue playback commands to the Spotify app. Spotify itself performs playback, networking, caching and system integration. This gives MOSAIC a credible route to a polished Spotify control surface, but not to ingest Spotify audio into MOSAIC's own Media3 player. The SDK requires user authorization and is documented as beta. Spotify's developer getting-started page also states that streaming applications may not be commercial and Spotify content must remain unaltered: https://developer.spotify.com/documentation/android/tutorials/getting-started.
- **YouTube:** YouTube's [Android background-play help](https://support.google.com/youtube/answer/7437614) says background play is a Premium feature in the YouTube mobile apps. The [YouTube developer policy guide](https://developers.google.com/youtube/terms/developer-policies-guide) explicitly disallows API services from allowing YouTube playback to continue when minimized/closed and from restricting ads that would otherwise play. Therefore the compliant target is source-owned YouTube playback with exposed session controls where available, not extracting audio into MOSAIC or stripping YouTube ads.
- **Ad filtering:** DNS/host rules can still block known separable third-party ad/tracker hosts across apps, but they cannot reliably identify same-host or in-stream ads. No universal ad-skip claim is made.
- **Next implementation split:** (1) integrate and test Spotify App Remote as a clearly labelled delegated source; (2) improve YouTube MediaSession discovery/control and document account/background requirements; (3) build MOSAIC-native adapters for direct URLs, radio and RSS, which can genuinely enter the shared Media3 queue; (4) test Ad Shield compatibility separately for each route.
